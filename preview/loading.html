Loading

A loading state promises the shape of what is coming, never how much of it. The shape of a row is fixed by the component; the count is a load-time fact the front end does not have. Design as if it never will.

Spinner in a fixed box
Tracked bills

Over-reserves. min-h-48 is a 192px guess made without a count — the same guess a skeleton makes, carrying no information. Usually settles by shrinking.

Five rows
Tracked bills

Claims a count. Right only when five arrive. A lie when one does, and it settles by shrinking too.

One row, no fixed height
Tracked bills

Under-reserves. One row is the floor of what can arrive, so the card can only grow — and growth pushes the page down, which is what a page does as it loads.

Shape
One skeleton row, the shortest plausible item. Header renders immediately — it is static and known, so only the body is skeletal and the moving region stays small.
Direction
Under-reserve, so the settle is always downward. A shrink pulls content up under a reader's eyes and a thumb already moving; that is the failure people notice.
Never
A min-height on a loading container. A count, a cached count, or a guess at one — resolving cardinality early is an architectural question and the design must be right without it.
Spinner
One job: an in-place indeterminate wait with no shape to promise — a button mid-submit, a control resolving. Never a route-level content fallback. One ink value in both modes.
Zero
Not a loading problem. No treatment fixes it and the spinner is worst — the user waits in an empty box and is handed an empty box. That is card-empty.
Motion
The pulse is arrival, not motion — sanctioned anywhere by motion.rules, costing nothing from the two-surface budget.
